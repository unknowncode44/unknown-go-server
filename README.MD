# Material Module

## Purpose

This module implements the **Material** domain of the system. It represents the internal catalog of materials used by the company to provide services. At this stage, the focus is exclusively on materials as catalog entities, independent from vendors, costs, quotations, or tasks.

The design follows a **clean, layered architecture** consistent with the rest of the server:

* HTTP layer (API) → *not implemented yet*
* Service layer (business logic)
* Repository layer (persistence)
* Entity layer (domain models)

This README documents what has been implemented so far and the rationale behind the design decisions.

---

## Scope (Current)

Included:

* Material entity definition
* Repository interface and GORM implementation
* Service interface and implementation
* PostgreSQL integration via GORM `AutoMigrate`

Explicitly excluded for now:

* Vendors
* Material–Vendor relationships
* Costs and pricing
* Quotations, tasks, certifications
* Authentication / authorization
* Events or asynchronous processing

---

## Domain: Material

A **Material** represents an item that can be purchased and installed as part of a service. Materials are not transformed; they are used as provided by suppliers.

### Core characteristics

* Identified by UUID
* Belongs to a business sector (e.g. electrical, radio frequency)
* Has a unit of measure
* Is never physically deleted (soft deactivation instead)

## Entity Definition

Location:

```
pkg/entities/material.go
```

### Fields

| Field         | Type      | Description                             |
| ------------- | --------- | --------------------------------------- |
| ID            | UUID      | Primary key, generated by PostgreSQL    |
| Name          | string    | Human-readable name                     |
| Sector        | string    | Business sector (e.g. electrical, RF)   |
| UnitOfMeasure | string    | Unit of measure (meter, unit, kg, etc.) |
| IsActive      | bool      | Business-level activation flag          |
| CreatedAt     | time.Time | Audit field (managed by GORM)           |
| UpdatedAt     | time.Time | Audit field (managed by GORM)           |

### Notes

* UUIDs are generated in the database using `uuid_generate_v4()`
* `IsActive` is used instead of deletes to preserve historical integrity
* `Sector` is currently a free string and may later evolve into a separate table

## Repository Layer

Location:

```
pkg/material/repository.go
```

### Responsibility

The repository is responsible **only for persistence**:

* It translates domain objects to database operations
* It does not contain business rules
* It does not know anything about HTTP or Fiber

### Interface

The repository exposes the following operations:

* Create a material
* Retrieve all materials
* Retrieve a material by ID
* Update a material
* Delete a material (physical delete, currently unused by the service)

All identifiers use `uuid.UUID`, and entities are passed as pointers.

### Design decisions

* GORM is encapsulated behind the repository interface
* No manual timestamp handling (delegated to GORM)
* `FindAll` returns a slice by value (idiomatic Go)

## Service Layer

Location:

```
pkg/material/service.go
```

### Responsibility

The service layer implements **business rules and use cases**. It orchestrates repository calls and enforces domain constraints.

The service:

* Validates required domain fields
* Prevents invalid state transitions
* Defines how materials should be created, updated, or deactivated

The service does **not**:

* Handle HTTP requests
* Format responses
* Depend on Fiber or GORM

### Use cases implemented

* Create material
* List all materials
* Get material by ID
* Update material
* Deactivate material (soft delete)

### Deactivation vs Deletion

Materials are not deleted from the database. Instead, they are marked as inactive:

* Preserves historical references
* Prevents integrity issues when costs or quotations are added later
* Reflects real business behavior

## Database & Migrations

* PostgreSQL is used as the database
* GORM `AutoMigrate` is responsible for schema creation
* The `uuid-ossp` extension is required and is installed at startup

```sql
CREATE EXTENSION IF NOT EXISTS "uuid-ossp";
```

This ensures UUID generation works consistently across environments.

## Architectural Principles Followed

* Clear separation of concerns
* Domain-first design
* Dependency inversion (services depend on interfaces, not implementations)
* Incremental modeling (no premature optimization)
* Future-ready for events and async workflows
